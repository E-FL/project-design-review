# One board, several conversations

Discover the canonical board from the project configuration or existing review folder before creating a review. Read the saved notes, issue queue, revision registry and current user context. A conversation owns only its explicitly authorized page/revision/issue scope; represent ownership with a non-secret worker/conversation identifier on the claim and show it with work progress. Do not send other conversations messages without direct user authorization.

Use one loopback server and protected queue. `expectedVersion` prevents competing claims or edits to an issue. Claim/check ownership before source edits and before completion; never approve another conversation's items. A page already being worked on must be deferred or coordinated under user authorization, not edited in parallel blindly. Different pages may complete independently through serialized publication. Publish a new immutable revision using the current history, not a cached whole-registry write. Preserve all page histories and feedback. Browser polling announces new results without replacing a historical view or unsaved edits.

Use `node review-worker.mjs inbox --pages P02` (comma-separated page IDs for an explicitly broader scope). Set `REVIEW_PAGES` for both inbox and update calls and `REVIEW_WORKER_ID` to the owning conversation's non-secret identifier, or include `workerId` in each action JSON. The helper rejects updates outside its configured page scope. The browser shows ownership and progress per page. The global inbox is for an explicitly authorized coordinator, not a license for a page worker to handle all items.

Verify with a disposable board: two workers claim two pages, both results survive; a stale claim/update is rejected; a duplicate revision cannot overwrite history. This proves local concurrency behavior, not automatic access to other agent conversations or a connected AI service. State the actual worker connection and cadence.
